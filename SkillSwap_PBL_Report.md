## ABSTRACT

SkillSwap is a comprehensive full-stack Java-based application designed to bridge the gap in peer-to-peer learning by allowing users to exchange skills without monetary transactions. The traditional method of acquiring new skills often involves expensive courses or unverified tutors. SkillSwap solves this by providing an intuitive platform where users can offer skills they excel at in exchange for learning skills they desire. The solution utilizes a modern technology stack consisting of a React-based frontend and a robust Java Spring Boot backend. Key programming concepts utilized include Object-Oriented Programming (OOP), modular RESTful API architecture, Exception Handling, and Data Transfer Objects (DTOs). The system implements database connectivity using Spring Data JPA and Hibernate, enabling dynamic CRUD operations for user profiles, skill matching, and real-time request management. The key outcome of this project is a fully functional, scalable web application featuring instant notifications, an interactive avatar system, and an automated session request pipeline. SkillSwap successfully demonstrates how Java technologies can foster collaborative learning, making skill acquisition accessible and mutually beneficial.

**Keywords:** Peer-to-Peer Learning, Java Spring Boot, REST API, Object-Oriented Programming, Skill Exchange.

## CHAPTER 1: INTRODUCTION

### 1.1 BACKGROUND
In today’s fast-paced digital world, continuous upskilling is vital for professional and personal growth. However, traditional education platforms and private tutoring are often highly expensive and inaccessible to students and early-career professionals. While massive open online courses (MOOCs) exist, they often lack the personalized, interactive guidance of one-on-one mentorship.

SkillSwap addresses this critical gap by creating a peer-to-peer ecosystem. It operates on a simple bartering principle: users can teach a skill they have mastered in exchange for learning a skill they desire, using a "Credits" system instead of money. This democratizes education, making it accessible to anyone willing to share their knowledge.

### 1.2 DRIVING QUESTION
“Can we develop a Java-based web application that can efficiently manage a peer-to-peer skill exchange platform, reducing the financial barriers to learning and fostering community collaboration?” 
We narrowed this into a concrete Java task by identifying the required modules: building secure user authentication, designing relational database entities using OOP concepts, implementing RESTful API connectivity using Spring Boot and JPA, and linking it to an interactive React frontend.

### 1.3 OBJECTIVES
- **To analyze** the real-world problem of inaccessible mentorship and identify the requirements for a peer-to-peer Java-based platform.
- **To design and develop** a Java application using appropriate OOP concepts, establishing clear Domain Models (User, Skill, Request, Exchange).
- **To implement** database connectivity and robust CRUD operations using Spring Data JPA and Hibernate.
- **To test and debug** the application to verify its functionality, ensuring smooth API communication and safe exception handling for edge cases (e.g., duplicate skills, invalid payloads).
- **To reflect** on the team's approach, division of frontend/backend work, and what the iterative development process taught each member.

### 1.4 SCOPE AND LIMITATIONS
**Scope:** The project covers a complete full-stack web application featuring user registration, dynamic profile management (with Base64 avatar uploads), a search/discover algorithm for finding mentors, and a real-time request/acceptance system for scheduling skill swaps.
**Limitations:** The current version relies on external tools (like Google Meet) for the actual video calls rather than an integrated WebRTC engine. Load testing for thousands of concurrent users has not been extensively conducted due to infrastructure constraints.

## CHAPTER 2: CONCEPT EXPLORATION

### 2.1 RELATED APPROACHES

#### 2.1.1 Traditional Java Application Approach
**Core Java / JDBC:** Building the application using pure Servlets, JSP, and raw JDBC queries. 
*Outcome:* Highly verbose codebase, manual connection pooling, and complex SQL exception handling. Difficult to scale and maintain for a modern RESTful architecture.

#### 2.1.2 Java Framework-Based Approach
**Spring Boot / Hibernate / REST API:** Utilizing the Spring Boot framework to automatically configure an embedded Tomcat server, and using Spring Data JPA to map Java Objects directly to database tables (ORM).
*Outcome:* Extremely rapid development, clean separation of concerns (Controller, Service, Repository), and seamless JSON serialization for modern frontend frameworks.

### 2.2 SUMMARY TABLE

| Ref. | Approach | Reported Result |
|---|---|---|
| [1] | Raw JDBC & Servlets | Slower development time, highly coupled code. |
| [2] | Spring Boot & JPA | Clean architecture, built-in REST support, highly scalable. |

### 2.3 WHAT THIS TOLD US
Based on our exploration, the team decided to adopt the **Java Framework-Based Approach** (Spring Boot) for Iteration 1. Modern web applications require rapid API iteration and robust JSON handling to communicate with JavaScript frontends. Spring Boot's built-in dependency injection, simplified database ORM (Hibernate), and `@RestController` annotations provided the most efficient and industry-standard pathway to build the SkillSwap backend.

## CHAPTER 4: ITERATIVE DESIGN AND DEVELOPMENT

### 4.1 SYSTEM ARCHITECTURE

**User Input (React UI) → Validation (Axios/JS) → Java Processing (Spring Boot REST) → Data Handling (Spring Data JPA) → Output (Database/JSON)**

*(Figure 4.1 — System Architecture Diagram)*

The system accepts user input through a React frontend, validates credentials and payloads, and sends HTTP requests to the Spring Boot application. The Java Controllers route requests to Services which apply business logic, and Repositories handle database persistence.

### 4.2 BASELINE
The first version implemented basic Java Classes (`User.java`, `Skill.java`) with hardcoded mock data. It worked correctly in memory using standard collections (Lists/Maps) to demonstrate the logic of matching a teacher to a learner, but lacked persistence and a graphical interface.

### 4.3 PROJECT REFINEMENT
The application was vastly improved by integrating **Spring Data JPA**. We replaced manual collections with relational database mapping. We introduced robust exception handling (`@ControllerAdvice`) to safely catch data truncation errors (e.g., when uploading large Base64 images for profiles).

### 4.4 FINAL APPROACH
The final application uses a fully decoupled client-server architecture. The backend is a modular object-oriented Java API utilizing Encapsulation (DTOs), Abstraction (Service Interfaces), and Spring's Dependency Injection. The frontend is a visually stunning Tailwind v4 application featuring real-time data polling, interactive modals, and secure route handling.

### 4.5 TESTING AND EXECUTION
The application was tested for REST API endpoint reliability, proper HTTP status codes, input validation (e.g., preventing duplicate skills), and exception handling. Testing confirmed that Base64 image payloads save correctly to the `@Lob` database column and that real-time notification events broadcast successfully across the UI.

## CHAPTER 5: IMPLEMENTATION

### 5.1 MODULE DESCRIPTION
The Java application is divided into layered modules to ensure the system is scalable and organized:
- **Controller Module:** Handles incoming HTTP requests and routes them (`UserController`, `ExchangeController`).
- **Service Module:** Processes core business logic, such as matching skills and executing exchanges (`UserService`, `ExchangeService`).
- **Data Management Module (Repository):** Interfaces with the database using Spring Data JPA (`UserRepository`, `SkillRequestRepository`).
- **Entity Module:** Defines the Object-Oriented representations of database tables (`User`, `UserSkill`, `SkillRequest`).

### 5.2 KEY CODE SNIPPETS

**Entity Definition with Large Object Storage:**
```java
@Entity
@Table(name = "app_users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String username;
    
    @Lob
    @Column(columnDefinition = "TEXT")
    private String profilePicUrl; // Stores large Base64 image strings safely
}
```

**Accepting a Skill Request Logic:**
```java
public Exchange acceptRequest(Long requestId) {
    SkillRequest req = skillRequestRepository.findById(requestId).orElseThrow();
    req.setStatus(RequestStatus.ACCEPTED);
    skillRequestRepository.save(req);

    Exchange ex = new Exchange();
    ex.setRequest(req);
    ex.setStatus(ExchangeStatus.IN_PROGRESS);
    ex.setStartDate(LocalDateTime.now());
    
    return exchangeRepository.save(ex);
}
```

## CHAPTER 6: RESULTS AND DISCUSSION

### 6.1 EVALUATION METRICS
- **API Response Time:** Critical for ensuring the React frontend feels snappy.
- **Database Persistence Success:** Ensuring complex relationships (One-To-Many User Skills) save without nested JSON looping errors.
- **UI Usability Check:** Ensuring background polling (every 15 seconds) for notifications successfully triggers UI updates without freezing the browser.

### 6.2 RESULTS ACROSS ITERATIONS

**Table 6.1 Iteration Results**

| Version | Test Cases Passed | Code Coverage | Performance (avg. response) |
|---|---|---|---|
| Baseline | Basic logic passed | 40% (Logic only) | ~5ms (In-memory) |
| Project Refinement | JPA mapping passed | 70% | ~45ms (H2 DB) |
| Final approach | Full API integration | 90% | ~60ms (Full HTTP cycle) |

### 6.3 DISCUSSION
The application performed exceptionally well in the final iteration. The decision to use Spring Boot drastically reduced boilerplate code. One major hurdle was encountering Jackson JSON Deserialization errors when passing nested `UserSkill` collections from the frontend to the backend during profile updates. This was resolved by actively sanitizing the payload on the frontend before dispatching the PUT request. Additionally, upgrading the database column to `TEXT` was a vital realization to support Base64 image uploads without external cloud buckets.

### 6.4 LIMITATIONS
- **Data Storage:** Base64 images in the database can bloat the database size over time; an external AWS S3 bucket would be preferable for large-scale deployment.
- **Real-Time Communication:** We used standard HTTP polling (every 15 seconds) for notifications rather than WebSockets (STOMP/SockJS), which creates slight delays and higher server overhead.
